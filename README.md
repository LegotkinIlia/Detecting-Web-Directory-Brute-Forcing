# Detecting-Web-Directory-Brute-Forcing

### Objective: 

Detect web directory brute-force attacks in Splunk by analyzing web server logs for abnormal request patterns, excessive 404 errors, and automated scanning behavior.


### Environment and Tools:

- SIEM: Splunk Enterprise installed on Ubuntu Linux.
- Attacker Machine: Kali Linux Virtual Machine.
- Target Machine: Ubuntu Virtual Machine (acting as the server).
  
### Steps:

### 2. Add Logs to Splunk

- Open the Splunk Web interface

- Go to Settings → Data Inputs → Files & Directories

- Click New Local File & Directory

- Enter the log path: `/var/log/apache2/access.log`

- At Set Source Type, choose `access_combined`

### 3. Launch the Kali Linux

On the Kali VM, use the built-in tool `dirb` to perform a web directory brute-force scan.

`dirb http://<UBUNTU_IP>`

This command sends a large number of automated HTTP requests to the target web server, attempting to discover hidden or non-listed directories and files by testing common paths from a wordlist.

<img width="1400" height="875" alt="L3 6" src="https://github.com/user-attachments/assets/cb038c14-7a44-4e53-87a3-97ff5ce5a157" />

Before running the attack, you need to ensure that port 80 (HTTP) is open on the Ubuntu target so the web server is accessible.

`sudo ufw allow 80/tcp
sudo ufw reload`

<img width="1120" height="780" alt="L3 5" src="https://github.com/user-attachments/assets/358a584b-2a88-4bbb-b277-625a9c114395" />

### 4. Analysis in Splunk

This search was implemented to manually extract the attacker’s IP and targeted web paths from the raw Apache logs.
Since the SIEM did not automatically parse these fields, the "rex" command was used to identify the high-volume 404 error pattern generated by the 'dirb' tool. This allowed me to convert raw log data into a clear statistical table, proving an automated directory brute-force attack was in progress.

`index=* sourcetype=access_combined status=404
| rex field=_raw "^(?<src_ip>\d+\.\d+\.\d+\.\d+)"
| rex field=_raw "GET (?<uri_path>\S+)"
| stats count by src_ip, uri_path
| sort - count`

### Summary:

After successfully configuring the UFW firewall to allow HTTP traffic, I executed the attack and captured the results in Splunk. The analysis revealed a massive spike in HTTP 404 (Not Found) errors.

- Attacker IP: 192.168.1.80
- Tool: Dirb
- Evidence: Over `4600` 404 errors were generated within seconds.
- Targeted Paths: The attacker attempted to access common sensitive directories such as /admin, /cgi-bin/, and /server-status.
- Mitigation: This detection allows security teams to identify automated scanners early and implement IP-based blocking or Rate Limiting to protect the web server from further exploitation.
